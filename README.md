# The Slate

A fixture-probability dashboard. It rates every team in twenty competitions from
completed results, prices each upcoming fixture as a home win / draw / away win split,
and ranks the day's slate so the most one-sided games sit at the top.

```
python3 build.py --days 4 --top 50    # pull data, rate teams, price fixtures
open dashboard.html                   # the dashboard
python3 backtest.py                   # prove it works, or doesn't
./refresh.sh                          # daily rebuild, safe to cron
```

No build step, no server, no dependencies beyond the Python standard library.

**Open `dashboard.html`, not `index.html`.** `dashboard.html` is a single self-contained
file with the data built in — it works anywhere, including emailed, dropped in a preview
pane, or opened straight off the filesystem. `index.html` is the template: it loads
`data.js` from alongside it, which is what you want when deploying, but it renders blank
if that sibling file is missing. Both are regenerated by `build.py`.

---

## What it actually does

**How accurate is it?** Backtested walk-forward across 4,605 matches of the 2025/26
season, each priced using only information available before kick-off:

| | model | baseline |
|---|---|---|
| Top pick correct | **49.3%** | 43.3% (always back the home side) |
| Log loss | **1.0171** | 1.0773 |
| Brier score | **0.6093** | — |

Ranked by confidence, which is what the dashboard is for:

| slice | fixtures | hit rate |
|---|---|---|
| Most confident 5% | 230 | **79.1%** |
| Most confident 10% | 460 | **73.5%** |
| Most confident 25% | 1,151 | 67.2% |
| Everything | 4,605 | 49.3% |

Reproduce with `python3 backtest.py`.

**It is worse than the betting market.** A model built on free league-table data has no
access to lineups, injuries, xG, or transfer fees. Bookmakers do, and a liquid market
aggregates thousands of informed opinions. Treat this as a tool for seeing which games
are lopsided and why, not as an edge over anyone.

## Why the algorithm isn't the one you might expect

The obvious scheme — points for wins, deductions for losses, add goal difference, add a
recent-form tally — has four problems, and I measured all of them:

**It double-counts.** League points already encode wins and losses. A separate win tally
weights the same signal twice.

**The scales are arbitrary.** A season goal difference of ±60 competing against a win
tally of ~90 is two numbers with no principled relationship. Nothing anchors the weights.

**It can't compare across leagues.** Coventry topping the Championship and Arsenal
topping the Premier League produce similar raw scores. They are not similar teams.

**A score difference is not a probability.** This is the real gap. Turning "Arsenal 84,
Coventry 31" into "72% home win" needs a calibrated mapping, and there is no honest way
to invent one from the score alone.

So the ratings feed a model that produces probabilities directly, and the raw table
statistics stay on screen as the reasoning layer rather than as the engine.

### Recent form does nothing

You may expect a last-5 form component to matter. It doesn't, and this is worth stating
plainly because it is counterintuitive:

| form weight | log loss | accuracy |
|---|---|---|
| 0.00 (disabled) | 1.0175 | 49.3% |
| 0.05 (shipped) | 1.0171 | 49.3% |
| 0.20 (aggressive) | 1.0181 | 49.3% |

The difference is inside the noise. Form is already contained in the season ratings;
last-5 points mostly resamples data the table already holds. It is kept at a capped
±5% because it can catch what a season aggregate misses — a new manager, an injury
crisis, a side that has stopped trying — and it is displayed on every row because it is
information you want to see. But it is not driving the numbers.

## The model

### Stage 1 — team strength

For each team, from completed results:

```
att = (goals scored per game)   / (league average per team per game)
def = (goals conceded per game) / (league average per team per game)
```

`att` above 1.0 means the side scores more than a league-average team. `def` below 1.0
means it concedes less. Both are shrunk toward 1.0, so a team with few matches is not
treated as though its record were settled.

**Crossing divisions.** A side's absolute quality is its rating relative to its league,
multiplied by that league's strength. To move a promoted or relegated team, re-express
that absolute quality against the new league's average:

```
att_new = att_old × (strength_old / strength_new)     # weaker attack going up
def_new = def_old × (strength_new / strength_old)     # leakier defence going up
```

Then shrink hard toward 1.0, because promoted and relegated sides are the least
predictable teams on any weekend.

**Blending in the current season.** Weight `w = played / (played + K)` with **K = 12**.

K=12 was fitted, not guessed, and it is roughly double what intuition suggests:

| K | log loss |
|---|---|
| 2 | 1.0334 |
| 6 | 1.0203 |
| **12** | **1.0171** |
| 20 | 1.0174 |

In backtesting, last season's table beat the current season's until about a dozen matches
had been played. Six games of new results is a small sample and the model does better
distrusting it. This matters most in August, which is exactly when the dashboard is
hardest to trust anyway.

### Stage 2 — the match

Expected goals for each side, with home advantage as a multiplier:

```
λ_home = att_home × def_away × μ × 1.155
λ_away = att_away × def_home × μ × 0.870
```

The 1.33 ratio reproduces the long-run English top-flight split of roughly
45% home / 26% draw / 29% away. Lower divisions run slightly higher.

Build the score matrix from 0–10 goals a side, apply the **Dixon-Coles** correction, and
sum the cells for home / draw / away. The correction matters: low-scoring results are not
independent, 0-0 and 1-1 happen more often than plain Poisson expects, and without it the
model systematically under-prices draws.

### Stage 3 — calibration

**The raw output was badly over-confident.** Measured on the backtest before correction:

| model said | actually happened |
|---|---|
| 88–100% | 77.4% |
| 75–88% | 75.3% |
| 50–62% | 49.6% |

Season-aggregate ratings know nothing about rotation, red cards, or a keeper having the
game of his life, so the true distribution is flatter than the model's. A temperature
term (**T = 1.15**) flattens every probability toward the 1/3 line. After correction,
every band lands within a few points of its stated confidence.

This is not cosmetic. Shipping the uncorrected numbers would mean the headline percentage
on every row was a lie. Re-fit T whenever the league strength table changes.

## The August problem

**The 2026/27 Premier League starts on 21 August 2026.** As shipped, *nothing has been
played*: 0 of 69 fixtures have any current-season evidence. Every number comes from
2025/26 carried forward.

That means the model does not know that Guardiola resigned, that Slot was sacked, that
Alonso is at Chelsea, or that any transfer happened this summer. The dashboard says so
prominently rather than hiding it, and unrated fixtures are visibly marked.

The hook for correcting this is **`adjustments.json`**:

```json
{
  "Liverpool": { "att": 0.96, "def": 1.06, "why": "Slot sacked, squad unsettled" }
}
```

Multipliers on expected goals; 1.0 is no change. Anything outside 0.80–1.20 is you
overriding the model rather than nudging it. Overrides are flagged in the UI with the
stated reason, so an adjustment is never invisible. Delete entries once the season has
enough matches to speak for itself.

## Coverage: what "all teams available to bet on" would take

Betting markets cover several thousand competitions worldwide. Free open data does not
come close, and this is the hard ceiling on the project rather than a gap in the code.

As built: **twenty competitions have ratings, ten have current-season fixtures.** That is
everything openfootball publishes for 2026/27 as of the build date. The biggest Saturday
in the window has 45 fixtures, so the top-50-per-day target is nearly met by luck rather
than by coverage.

To go wider you need a paid feed. `sources.py` normalises every source into
`(date, home, away, home_goals, away_goals)` tuples, so adding one is a reader function
and a row in `FIXTURE_FILES`:

| source | cost | competitions |
|---|---|---|
| [football-data.org](https://www.football-data.org) | free / €12mo | 12 |
| [API-Football](https://www.api-football.com) | free / $19mo | 1,200+ |
| [football-data.co.uk](https://www.football-data.co.uk) | free | 20+, 30 years of history |

Note that **ratings are the binding constraint, not fixtures.** A fixture you cannot rate
both sides of is worthless — it renders as "not rated" and sorts last. Adding a league
means adding at least one completed prior season for it too.

## Data sources

**Primary: [openfootball](https://github.com/openfootball).** Public domain, no API key,
no rate limit worth worrying about. Historical results come from `football.json`;
current-season fixture lists come from per-country repos.

**Not BBC.** Scraping it breaches their terms, the markup changes without warning, and
there is no stable identifier for a fixture. Every table-scraping approach to this
problem eventually dies the same way.

### Known gaps

openfootball is volunteer-maintained and its coverage of *current-season* fixture lists
lags its coverage of completed seasons.

Teams promoted from a division the build doesn't cover (Belgian and French second tiers,
mostly) have no rating at all. Those fixtures are marked "not rated", faded, and sorted
last under every ordering, because a placeholder number should never sit at the top of
the slate pretending to be a read.

### Upgrading the source

To reach genuine 50-a-day coverage, layer a live API over the top:

| source | cost | coverage | notes |
|---|---|---|---|
| [football-data.org](https://www.football-data.org) | free / €12mo | 12 competitions | 10 req/min free, most reliable free tier |
| [API-Football](https://www.api-football.com) | free / $19mo | 1,200+ competitions | free tier capped at 100 req/day |
| [football-data.co.uk](https://www.football-data.co.uk) | free | 20+ leagues, 30 yrs | CSV downloads, excellent for backtesting |

`sources.py` normalises everything into one shape, so a second source only needs its own
reader function returning `(date, home, away, home_goals, away_goals)` tuples. Cache
aggressively: standings change once a day and historical results never change.

### Calibrating league strength

The `strength` values in `engine.py` are **hand-set priors and the weakest part of the
model.** They are ordinary judgement calls about how a mid-table Championship side
compares to a bottom-three Premier League side.

To replace them with fitted values, collect inter-league results — European competition
matches, and the first season of every promoted and relegated team — then solve for the
strength vector that minimises prediction error across those matches. A few hundred
cross-league fixtures is enough to beat guesswork.

## Files

| file | what it is |
|---|---|
| `engine.py` | ratings and the match model. Every number on screen traces to a function here |
| `sources.py` | fetching and parsing. Add new data sources here |
| `build.py` | rates teams, prices fixtures, writes `data.json` and `data.js` |
| `backtest.py` | walk-forward evaluation, calibration table, hyperparameter sweep |
| `dashboard.html` | **the dashboard.** Self-contained single file, data built in |
| `index.html` | the same page as a template, loading `data.js` from alongside it |
| `adjustments.json` | manual per-team overrides for what the model can't see |
| `refresh.sh` | daily rebuild, safe to cron, keeps snapshots |

`build.py` writes three things: `data.json` for anything else you want to build against,
`data.js` for `index.html` to load (a `window.__FIXTURE_DATA__` shim, because a bare
`fetch()` of a local JSON file is blocked by CORS on `file://` URLs), and
`dashboard.html` with everything inlined.

## Reading the dashboard

Each row is one fixture, with the probability bar between the two teams. All bars share
one axis and a 50% reference line, so fifty stacked rows read as a chart: any home block
crossing the line is odds-on. Click a row for the full record on both sides and a
plain-English account of where the edge comes from.

Sort by **Most one-sided** for the strongest reads, **Away edge** for likely upsets,
**Goals** for expected total, **Kick-off** for chronological order.

## Scoring your own predictions

`refresh.sh` archives every build to `archive/data-<timestamp>.js` and keeps a fortnight.
Once results land, join a snapshot against them to measure live accuracy the same way
`backtest.py` measures historical accuracy. A model that isn't being scored is a model
you don't know anything about.

## Limitations, in one place

- Worse than the betting market. Always will be, on free data.
- Knows nothing about lineups, injuries, suspensions, or transfers.
- League strength coefficients are hand-set judgement, not fitted.
- Current-season fixture coverage is 10 of 20 competitions, nowhere near every bettable market.
- Flags mark the competition's country, so both sides of a domestic fixture share one.
- Cold-start accuracy (under 6 matches played) is 47.9%, below the 49.3% full-season figure.
- Kick-off times come from the fixture list and are not corrected for TV rescheduling.
- Nothing here is betting advice.
