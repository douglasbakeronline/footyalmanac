## Schedule and idempotency

- `due(now_uk)`: the daily from 07:00 to 11:59 UK, the weekly in the same window on Saturdays. Outside it
  nothing is sent and the log says so; a missed morning is skipped, never sent in the evening. The morning
  briefing slot (07:00 UK, `claude/briefing-chain-2026-11-16.md`) is the build expected to send.
- deploy.yml runs `python3 mailer.py` after `daylist.py` (today's list is pinned late in the build) and after
  groupings, scale and slip, `continue-on-error: true`.
- A daily whose `daylist.json` is for another day, or with no `groupings-data.js`, is skipped and logged.
- Order: build both variants, `almanac_mail_list`, then `almanac_mail_claim`, then send. The claim is true
  only for the first caller per kind and day, so two builds never both send; nothing is claimed if the
  list cannot be read or the email cannot be built.
- Resend's batch endpoint, at most 100 emails a call, one email per recipient, half a second between
  calls. A 429, a 5xx or a lost connection is tried twice more (2s, 4s) with the same `Idempotency-Key`
  (`almanac-<kind>-<day>-<batch>`), so a retry after a lost reply never sends twice; any 2xx ends it, a 4xx
  is not retried. The log prints counts and HTTP codes only, never an address.

## Unsubscribe and manage

Every email carries `List-Unsubscribe: <https://nangcsyicqfvfawyvkus.supabase.co/functions/v1/almanac-unsubscribe?t=TOKEN>`
and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, the same link in the footer, and
`https://sportsalmanac.bet/#mailer?manage=TOKEN`. TOKEN is the row's `manage_token`; a row whose token is not
a UUID is never mailed.

On the page, a script at the top of `<head>`, before Tag Manager, GA4 and Cloudflare, reads
`#mailer?confirm=` or `#mailer?manage=`, keeps the token in `window.__MAILER_TOKEN__` and replaces the
address with `#mailer`. The Mailer script takes it from there (`window.mailerToken`) and clears it; a link
opened in a page already loaded reaches it through `navApply`, and `navWrite` writes back `#mailer` only.
The token is never shown, stored or logged.

## RPC contracts

Read from the live functions on 23 Nov 2026:

- `almanac_confirm(p_token uuid) -> boolean`
- `almanac_get_preferences(p_token uuid) -> table(email_masked, daily, scale, sunday, status, paused_until)`:
  PostgREST returns an array of one row, or none for an unknown token.
- `almanac_update_preferences(p_token, p_daily, p_scale, p_sunday, p_paused_until, p_unsubscribe) -> boolean`.
  A null `p_paused_until` clears a pause, so the page sends the current pause back when "Keep the pause"
  is chosen. Resubscribing an unsubscribed row sets it `pending`; nothing sends a new confirmation email
  for that yet, and the page says the address must be confirmed again.

The page also accepts an object with `ok: true` for any of the three. Coded against, created by the lead
(not in the repo): `almanac_mail_list({p_secret, p_kind}) -> [{email, manage_token, scale}]` and
`almanac_mail_claim({p_secret, p_kind, p_day}) -> boolean` (a one-row table or `{x: true}` also read).
